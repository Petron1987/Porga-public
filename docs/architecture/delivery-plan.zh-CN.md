# 从 v0.2 到长期目标的交付计划 · A1

阶段按能力和验收推进，不按版本数字推断完成度。以下没有承诺工期或自动扩张权限。
每阶段都保留上一阶段可运行路径，先用公开/合成数据与离线模型验证机制，再在明确
授权和已配置 Key 的条件下验证真实模型。任何阶段均不能自动创建/推送 GitHub。

2026-11-05 实现更新：v0.3 已交付 M1 的有限首片——章程澄清/版本授权、两种受限
交付团队、组织与任务图快照、成果接受及旧数据迁移。75 项离线测试通过。
完整 M1 的通用候选团队、复用生命周期与更丰富的协议仍待后续验收；下方保留目标要求，
不把两种固定交付类型推广为任意目标组队能力。参见 [实际边界](../m1-projects.zh-CN.md)。

## 基线 B0：已经存在

2026-11-06 实现更新：v0.4 新增外部项目契约 v1、公开 SDK/CLI、资料/外发/状态隔离、
精确包版本锁定及独立安装包验收。属于 M1 的外部接入扩展，不表示完成通用动态组队或 M2 调度。
详见 [外部项目契约](../external-project-contract.zh-CN.md)。

v0.2：固定 Chief -> Research/QA、类型化输入输出、持久成果、来源/精确引用/QA 门禁、
预算、审批记录、去重、恢复、取消、完整性和备份。45 项测试验证这些边界。
B0 当时没有动态组织、长期知识晋升、真实候选实验、采用/回滚或后台调度。

## M1：完整项目协议与受限组织注册

覆盖 R07–R11、R30、R03/R35 的通用边界。

交付：Project Charter、CapabilitySpec、AgentDefinition、OrganizationRevision/Binding、
项目/角色注册表和校验器。Chief 根据目标从已批准能力注册表形成候选团队与任务图；
可选择复用 Chief/Skill，不能强制每次创建相同角色，也不能自行创建带新权限的工具。
加入 [启动澄清与目标验收](project-genesis.zh-CN.md)：先用已有资料形成章程建议，集中
确认关键目标、验收、边界与资源；显式记录授权与假设，避免让 Owner 微管理实现细节。

验收：
- 至少两类不同目标产生不同、可解释的有效团队/任务图；不足以断言普遍组队有效。
- 超预算、缺少验证者、未知角色/工具、循环依赖或无限轮次被确定性拒绝。
- 一项任务的实际权限始终是各层政策交集，不能靠生成角色升级。
- 旧 v0.2 示例和数据仍可读；新协议有迁移/版本及回滚运行入口。
- 已确认事项不重复问，关键授权缺口不默认放行；最终成果接受与任务完成/发布批准分开。

失败处理：候选未通过不激活；允许返回明确能力缺口和待决项，不伪造成功。

## M2：持久任务图与本地持续调度

覆盖 R11、R23/R24，前置 M1 的任务/版本协议。

交付：Task/Attempt 分离、Outbox/Inbox、单 Worker、租约/代际、有限重试/对账、
Scheduler、停止条件和聚合通知。先维持单 Worker，再通过并发实验决定是否解除整库锁。
外部学习的 ResearchWatchSpec 使用相同调度/配额，先做受限增量扫描；不能另起无限搜索循环。

验收：
- 领取前后、外部请求后、保存成果前后等故障点注入崩溃，验证恢复和未知结果处理。
- 重复投递、计时器重启、错过触发不会重复逻辑任务或无限补跑。
- 过期 Worker 的结果被代际检查拒绝；未知外部动作进入对账而非盲目重做。
- 取消、预算与优先级在持续 Worker 中可用；关机不宣称仍在线。
- 一次有限本地持续运行演练有明确持续时长、工作量、费用和恢复记录，由 Owner 决定通过线。

失败处理：dead letter/隔离和人工升级，保留所有 Attempt/回执，不靠删除账本恢复运行。

## M3：项目知识与 Skill 晋升

覆盖 R17–R19，使用 M1 的项目身份和 M2 的可追溯执行。

交付：六类 MemoryRecord、来源/适用条件/有效期、矛盾和撤销、项目范围检索、
声明式 SkillPackage。先项目内复用；跨项目平台晋升默认关闭，待独立授权和脱敏验证。
同时支持 [文章/视频的来源卡片与覆盖范围](external-learning.zh-CN.md)，区分原文、目录、
字幕/转录、实际画面与二手解读，不把“总结过”当作“证实并采用”。

验收：
- 新任务只能读取作用域内、状态允许的知识；提示词请求别的项目不能绕过过滤。
- 来源过期/撤销后，能找到受影响成果/Skill，阻止继续默认使用。
- 原始聊天不能直接进入 active Fact/Skill；“被保存”不等于“已核验”。
- Skill 的输入输出、权限、版本和测试可复现；不执行任意生成代码。

失败处理：quarantine、回到待核验、停止晋升；保留冲突信息而不静默覆盖事实。

## M4：第一次被独立证明的能力改进

覆盖 R13/R14/R15、R34 和 R32 的最小可测切片；前置 M2/M3。

交付：诊断证据、一个实际 Prompt/声明式研究 Skill 候选、冻结的基线/留出集、
案例级结果、费用、ApprovalRecord、ReleaseManifest 与回滚指针。先以人工批准采用。
外部方法提出的改进假设同样走这条实验/采用流程；平台权限和评估政策不由学习链自改。

验收：
- 原文引用、质量、安全等硬门禁全部通过，并满足预先定义的改善目标；报告失败和未知。
- 候选不得改评估规则/留出数据，数据泄漏与选择性删案例测试能阻止采用。
- 候选或政策在批准后变化，采用被拒绝；重复采用消息只产生一次活动代际变化。
- 模拟数据可验链路，只有真实代表任务与独立结果才可宣称模型能力改善。
- 发布异常后可回到兼容版本，旧任务固定旧发布，外部副作用有对账记录。

失败处理：拒绝采用、保留负结果与 Lesson；不因路线图需要“进化成功”降低通过标准。

## M5：组织拓扑演化

覆盖 R10/R12、R16 的组织/协作部分及 R39 的受控自治；前置 M4 的评估/发布基础。

交付：拆分/合并/替换/停用候选，完整职责/记忆/任务迁移计划，新旧组织对照，
临时执行者与长期专家生命周期，采用后监控。低风险自动采用仍需独立的 Owner 政策决定。

验收：
- 在同类任务和等价验收条件下，证明质量/经济性或协调结果的改善，没有权限/验证独立性回归。
- 退役不遗留孤儿任务，历史成果仍可追溯到旧角色和版本。
- 合并不能把独立 QA 职责直接并回被测 Agent；拆分不能悄悄扩大总预算。
- 失败的组织候选可以停用/回退，不自动将其经验提升为平台规则。

## M6：领域实例与持续业务反馈

覆盖 R20/R35、R32 的业务价值和决策维度；可在 M1 后提供合成 Blueprint，完整进化
验证仍依赖 M4/M5。初期领域模板仅使用公开或合成资料。

验收：同一 Kernel 能运行至少两个不同领域 Blueprint，领域规则留在模板/适配层；
目标、假设、外部证据和里程碑形成可追溯反馈，不将模拟结果报告成真实业务收益。
使用真实业务数据或执行生产动作，需要另行明确范围与验收条件。

## M7：跨设备与多人服务（另行范围）

覆盖 R26、R31 和 R40 的平台方向。触发条件是明确需要共享状态/常驻服务，而不是
为了“架构完整”提前部署。需要服务端认证/授权、中心数据库、对象存储、备份/恢复、
并发一致性、费用治理、可观察性及数据政策。先做迁移与故障演练，再面向其他用户。

涉及多日工作流/复杂外部等待时，比较 Temporal 等成熟引擎与本地队列的维护成本。
引入新后端不替换现有领域 ID、Policy、账本和动作对账规则。

## P0–P4 与上述阶段的关系

| 原能力阶段 | 本规划对应 | 晋级依据 |
|---|---|---|
| P0 Kernel | B0 + M1/M2 的治理基础 | 受限组织与可靠任务可验证 |
| P1 Autonomous Team | M1 + M2 的团队实际任务 | 按目标形成团队并完成被验收工作 |
| P2 Learning Organization | M3 + M4 | 可复用知识/Skill 与独立改善证据 |
| P3 Adaptive Organization | M5 | 组织变更经对照带来净收益 |
| P4 Autonomous Enterprise | M6 + 持续运行/必要 M7 | 授权内持续业务结果、复盘与可靠升级 |

同一阶段有多个能力门槛，不使用软件 v0.x 数字替代验收，也不提供未经测量的完成百分比。

## 当前优先实现顺序

2026-11-06，Owner 确认新增以下对外接入主线：SDK/CLI 轻量启用 → 薄层 Skill →
MCP → 按实际需求建设 Worker 和 HTTP 服务。完整范围见下一节。

这条主线细化 M1 的接入体验并衔接 M2/M7，保留 M1–M7 的能力依赖与验收要求。
需要长任务可靠性时仍先具备必要的 M2 基础；接入协议不能替代队列、恢复或独立验证。
知识复用和候选改进继续按 M3/M4 验收，证明一次可复现改进后再做 M5；行业模板可早给
合成样例，但不提前开放业务权限。持续经营和多人平台仍有独立验收。

## 外部接入与分发的四步交付顺序

来源：Owner 于 2026-11-06 明确要求纳入总体规划。性质：已确认的交付方向，
尚未实现的功能保持待交付状态；本次仅更新规划，软件仍为 v0.4.0。
各入口共享同一内核和项目服务，业务项目及其私有数据继续独立于框架源码。
公开 GitHub、发布 Python 包、开放 MCP、运营 HTTP 服务分别需要具体发布决定。

### 第一步：SDK/CLI 的轻量启用体验

归属：M1 外部接入扩展。已有 SDK/CLI 和外部契约 v1，轻量初始化与自动摸底待实现。

交付：从选定项目目录开始，显式启用后生成项目配置、受限盘点结果、证据清单和章程
草案；复用已知信息，集中询问目标、资料范围、资源和验收的关键缺口，减少手填摘要
与配置。文档解析适配按类型和覆盖范围逐步提供，保留来源、章节和提取限制。

验收：
- 半成品、草稿和资料目录可进入接入/澄清，不要求先有完整 PRD、代码或 Git 仓库。
- 安装或 import 本身不扫描项目、不发起模型调用、不启动后台进程。
- 一次显式启用后，在获准范围内自动盘点并生成可审阅配置；缺目标、缺资料或无模型
  可用时记录待决项和下一步，不伪造分析或因项目不成熟拒绝登记。
- 路径、数据外发、预算和写入权限继续由契约执行；重复启用不覆盖原资料或复制整个项目
  到框架仓库。新增解析器不得把摘录覆盖冒充全文覆盖。

### 第二步：薄层接入 Skill

归属：接入适配层，待实现。该 Skill 教已有 AI 助手正确使用 Porga，独立于 M3 的
知识/Skill 生成、评估和晋升机制；发布一个接入 Skill 不代表实现学习能力。

交付：使用说明、触发条件、必要模板和最少包装脚本，调用稳定 SDK/CLI；引导助手完成
启用、澄清、提交已授权任务、查看成果与故障处理。任务和授权状态仍由内核持久化。

验收：
- 支持该 Skill 格式的宿主可对独立合成项目完成接入和任务调用，并明确未支持的宿主。
- 不复制组织、预算、审批或恢复逻辑形成第二套执行内核，不把提示词当权限执行机制。
- 不通过 Skill 向模型提供自批准、预算增额、任意命令或项目外文件访问能力；关键决定
  进入可信 Owner 确认路径，失败时保留可检查的内核结果。

### 第三步：MCP 结构化调用接口

归属：同一应用服务的协议适配，待实现。以有限、可验证的工具集合供 AI 助手使用，
例如项目预览、提交已授权任务、查询状态、读取成果、请求取消；具体工具名另行定义。

验收：
- SDK/CLI/MCP 对同一输入使用相同授权、版本、预算、隔离和验证规则。
- 输入有结构化校验，错误与未支持能力明确；跨项目读取、未授权执行和模型自批准被拒绝。
- 首个客户端完成独立合成项目闭环，验证重复提交、取消、失败与断开连接的实际语义。
- MCP 本身不承诺持续调度或长任务可靠性；需要这些能力的工具以相应 M2 验收为前置。
- 明确本地/远程文件边界，远程服务不得假定能直接读取使用方的本机路径。

### 第四步：按需求建设 Worker 和 HTTP 服务

触发条件：出现明确的长期后台运行或远程访问需求。归属：本地持久 Worker/队列/调度
属于 M2；共享或跨设备的服务、认证、运维和隔离属于相应 M7 范围。两者不捆绑发布。

交付与验收：
- 本地 Worker 可先独立运行，具备持久任务、恢复/对账、取消、预算、运行窗口与停止条件；
  用有限演练证据验收，不把安装进程或 MCP 连接视为已具备 24 小时运行能力。
- 需要 HTTP 时提供项目身份与授权、任务/成果接口、幂等与状态查询，继续复用同一内核；
  远程可达、多人共享和实际部署各自明确数据、运维与发布责任，不默认开放公网。
- 多项目总预算协调、迁移、备份及并发能力按实际服务范围补齐并验证。
- 知识晋升、组织拆分合并、真实候选采用与回滚继续遵守 M3–M5；增加服务入口不会自动
  满足这些能力门槛。A2A 保留为出现跨系统独立 Agent 协作需求后的评估方向，不插入近期主线。
